# Building a Two-Laptop GPU Training Cluster: An Engineering Writeup

## What this is

A distributed training system that links two consumer Windows gaming laptops — an RTX 5060 and an RTX 5070, each with 8GB of VRAM — into a single cluster capable of running real multi-GPU distributed training jobs, coordinated from a web dashboard, with zero specialized hardware and zero cloud spend. It exists to support a computer-vision research project (an agricultural crop-disease detection system) that needed more training throughput than either laptop could provide alone.

This is not a toy demo. Every claim below is backed by a real, reproducible test or a real production incident — not a design document describing what the system is *supposed* to do. Where something failed, the failure and its root cause are documented alongside the fix, because that's usually the more instructive part.

## The core engineering problem

Windows has no NCCL backend for PyTorch. NCCL — NVIDIA's collective-communication library — is what lets multiple GPUs, especially across machines, actually synchronize gradients during distributed training. On native Windows, PyTorch's distributed package doesn't have it at all. The workaround (falling back to the `gloo` backend) looks like it should work, but segfaults specifically on the backward pass, inside PyTorch's own C++ internals — not something fixable from application code. This was root-caused directly, not assumed: a minimal reproduction (init → build model → one batch → forward → backward) was run in isolation and confirmed the crash was `gloo`-specific and backend-independent of anything in the training script itself.

The fix: run the actual training inside WSL2 (Windows Subsystem for Linux), where a genuinely Linux PyTorch build with real NCCL support is available. Windows hosts the networking and orchestration layer; WSL2 hosts the GPU compute. This split shapes almost every subsequent design decision in the system.

## Architecture

Four layers, each independently useful and independently testable:

**Layer 1 — Networking.** Tailscale, a mesh VPN, connects the two laptops regardless of which physical network each is on. It runs on the Windows host, not inside WSL2 — verified via research, not assumption, that WSL2's default network interface MTU (1280 bytes) is too small to also carry a WireGuard-encapsulated Tailscale tunnel on top, a documented Tailscale/WSL2 interaction. Windows 11's WSL2 "mirrored" networking mode is the piece that makes a Tailscale connection reaching the Windows host also reach whatever's listening inside WSL2.

**Layer 2 — Coordinator and worker daemon.** A worker daemon runs on every contributing machine (including the "main" one), exposing a small HTTP API: report status and GPU health, accept a job dispatch, run an authenticated remote command, and pull a dataset from another machine. A coordinator on one machine polls all workers, computes rank assignment for a distributed job, and dispatches it. Both are plain-stdlib Python — deliberately no framework, since the actual job (spawn a subprocess, report its state) doesn't need one.

**Layer 3 — Job specs.** Training jobs are described in YAML files that reference a specific, already-reviewed script in the repository at a pinned commit — never arbitrary code. A worker will only ever launch a script from an explicit allowlist; a job spec pointing anywhere else is refused, even if the file genuinely exists in the repo. This is a hard line that was deliberately drawn early and preserved throughout: a coordinator can dispatch *data* to a worker, never *code*.

**Layer 4 — Dashboard.** A single-page web app showing live machine status, GPU utilization, and running jobs, with real action buttons (dispatch a job, run a command, check health) — not a static mockup. It talks to a small control API on the coordinator, which itself is just a thin HTTP wrapper around the same functions the command-line tool already used.

## The setup problem, and solving it properly

The first version of this project required a human to manually install WSL2, install Tailscale, configure networking, install PyTorch with the right CUDA build, generate security tokens, and remember to manually restart the worker process every time the machine rebooted. That's a real barrier to actually using a second machine — and it showed, directly, in how long it took to get a second real machine online.

The fix was a single script, `setup-worker.ps1`, that chains the entire sequence: WSL2 install, Tailscale setup with mirrored networking, the WSL2-side Python/PyTorch/NCCL environment, token generation, and — critically — registering the worker process as a Windows Scheduled Task that starts automatically at login and restarts itself up to three times if it crashes. Three things are explicitly *not* automated, and the script says so rather than pretending otherwise: a Windows reboot if WSL2 wasn't already present (a genuine OS-level requirement), Tailscale's one-time interactive login (an OAuth flow that can't be scripted without capturing credentials, which this project will never do), and the Administrator elevation prompt itself.

A USB-deliverable bootstrap script and a plain-language user manual were built for handing this off to a second person (the actual owner of the second laptop) with zero prior context on the project — covering exactly the three points above as expected interruptions, not failures, and telling them precisely what to send back and why not to share it publicly.

## Real bugs found in production, not in review

Every one of these was found by actually running the system against a real second machine, not by reading the code and reasoning about what might go wrong. Several were only visible because a second, genuinely different machine exposed an assumption baked in from developing against one machine alone.

### A PowerShell parsing ambiguity that caused a silent, permanent failure loop

A single line — `[regex]::Escape($WslDistro -replace "\s+", "")` — throws `Cannot find an overload for "Escape" and the argument count: "2"` at runtime on Windows PowerShell 5.1. PowerShell's static-method-call parser reads the unparenthesized `-replace` as a second positional argument to `Escape()`, not as part of the expression producing the first one. The script's own error handling let this exception pass silently, which meant a WSL2-detection check that should have said "already installed" always returned false. Every run re-attempted a full WSL2 install, hit a transient network error partway through, and then reported "reboot required" on every subsequent run forever — an infinite loop with no way out, discovered only because the second machine actually hit it. Fixed by wrapping the expression in parentheses; confirmed by reproducing the exact error and then confirming the fix resolves it, not by inspection alone. The deeper lesson, now documented in the code itself: a syntax check (does the script parse?) is not the same as a runtime check (does this specific expression bind its arguments the way I think it does?) — this class of bug passes the former and fails only the latter.

### Line-ending corruption from a missing `.gitattributes`

A shell script, correct and LF-only in the repository's own git history, arrived on the second machine with Windows-style CRLF line endings baked in — because Git on Windows commonly rewrites line endings on checkout depending on a per-machine configuration setting, and nothing in the repository told it not to. Bash cannot parse a script with CRLF endings; every line effectively carries an invisible trailing character, breaking string comparisons and, at end-of-file, breaking shell syntax parsing outright. The repository's own working copy didn't show the problem, because its files had been edited in place after an earlier checkout rather than freshly pulled under the machine's current settings — precisely the kind of silent, machine-dependent inconsistency a `.gitattributes` file exists to eliminate. The fix was verified by actually forcing a fresh clone with the same Git configuration the second machine used, and confirming the file came out correct — not just assumed from reading the new rule.

### A command-injection vulnerability, found by an automated security review and fixed same-day

The code that launches a training job inside WSL2 built a shell command by directly interpolating values — a machine address, a port number, a batch size, a filesystem path — that arrived over the network in a dispatch request. A background security review flagged this correctly: a crafted value like a master address of `127.0.0.1; touch /tmp/pwned` would have executed an arbitrary second shell command on the worker. The fix validates each field against what it's actually supposed to be — a real IP or hostname, an integer in the valid port range, a plain integer, a path made only of safe characters — rather than merely escaping shell metacharacters, matching a pattern already established elsewhere in the codebase (an explicit allowlist of which scripts can ever be launched, and which environment variables can ever be passed through). The fix was proven, not just written: a permanent automated test sends the exact injection payload through the real HTTP endpoint and confirms it's rejected before any shell command is built, and a separate direct check inside WSL2 confirmed the injected command genuinely never ran.

### A dataset path baked in at build time broke on a second machine — twice

A generated dataset configuration file included an absolute Windows path from the machine that built it. Moving that dataset to a second machine with a different folder layout broke training immediately: the path simply didn't exist there. The first fix — setting the path to `.` (meaning "here") — was based on an incorrect assumption about how the training library resolves that value; it turned out to resolve relative to the *training process's working directory*, not the configuration file's own location, which happened to still be wrong in a different way. Reading the library's actual source code (not its documentation, not an assumption) revealed the real rule: omitting the path setting entirely causes it to fall back to the configuration file's own directory — genuinely portable, because it's derived from wherever the file actually is on whichever machine loaded it, rather than any value baked in ahead of time.

### A systemwide broken package install, invisible for months because nothing had exercised it

Training the segmentation model crashed at first attempt with `RuntimeError: operator torchvision::nms does not exist` — a real incompatibility between the installed PyTorch build and its companion image-processing library. The investigation that mattered: checking whether this was specific to the second machine, or present on both. It was present on *both*, identically, meaning it had been part of the original environment setup from the very beginning of the project and had simply never been exercised — the earlier detection-only training never happened to import that specific code path. A clean reinstall targeting the correct CUDA build fixed it on both machines, confirmed by successfully importing both libraries together afterward — not just by re-running pip and hoping.

### "More GPU capacity" made things worse before it made them better

Asked to make fuller use of a laptop's GPU during training, the first change (doubling batch size, and raising the data-loading worker count from zero to eight) was reasoned from real measurements: the GPU was sitting at 43% utilization with plenty of unused memory headroom. But the result was a genuine regression, not an improvement — training speed collapsed by more than tenfold within thirty batches, and the WSL2 environment itself became briefly unresponsive to basic commands, timing out with a real Windows-reported service-level error. The cause, confirmed by direct observation rather than assumed: eight simultaneous data-loading processes reading dataset files across the WSL2-to-Windows filesystem bridge overwhelmed that bridge specifically, not the CPU or the GPU. Dialing back to four workers (still meaningfully more than zero) resolved it completely — sustained GPU utilization rose from 43% to roughly 80%, with no further instability, confirmed by watching it hold steady over several minutes rather than trusting one good reading. The lesson, now written directly into the code as a warning against re-attempting the naive fix: more parallelism is not automatically better when a shared resource other than the GPU is the actual bottleneck, and that bottleneck won't show up in GPU utilization numbers at all.

### Windows process detachment does not mean what it appears to mean

Launching a long-running background training process from a remote command consistently and silently failed to actually persist — the launch command reported success, but the process was gone moments later. Standard approaches (`nohup`, `disown`, `setsid`) inside a `bash` command invoked from Windows, and even PowerShell's own `Start-Process` with a hidden window, both failed the same way: the child process's survival was still tied to the lifetime of the parent process that launched it, contrary to what those tools are supposed to guarantee. The fix that actually worked was routing the launch through the Windows Task Scheduler — writing the launch command to a small batch file and invoking it as an immediate one-time scheduled task — because Task Scheduler genuinely detaches a process from its invoking context at the operating-system level, which none of the application-level detachment mechanisms reliably did in this specific remote-execution context. This is the same underlying mechanism already relied on for the worker daemon's own auto-start behavior, applied to solve a second, independently-discovered instance of the same class of problem.

## What actually got proven, end to end

- A worker daemon and coordinator, running on two genuinely separate physical machines connected over a consumer mesh VPN, successfully performed real distributed-training rendezvous — not a loopback test, a real cross-machine NCCL handshake, confirmed live.
- A real multi-hour distributed detection-model training job ran across both machines simultaneously, dispatched entirely through the coordinator rather than by hand-typing commands on each machine separately — the first time in the project's history this had happened through the system rather than around it.
- A second, independent training run (image segmentation, on the same disease-classification task) ran to completion on one of the two machines, reaching 91 training epochs before its own early-stopping criterion correctly triggered, producing a real trained model that was retrieved back to the coordinator machine and verified byte-for-byte intact.
- A security vulnerability was found by automated review, confirmed exploitable, fixed, and the fix was proven with a real attack attempt that was blocked — not merely reasoned about.
- A complete, previously undiscovered environment defect (the broken image-processing library) affecting *both* machines was found only because a new kind of training job finally exercised the code path that had been silently broken since the project's earliest setup.

## What this demonstrates

Distributed systems fail in the boundary conditions, not the happy path — and the boundary conditions here were real: a second physical machine with its own OS quirks, its own network hiccups, its own subtly different filesystem layout, and its own copy of a months-old broken package install nobody had noticed. Every failure above was found by actually running the system against that second machine and taking the resulting error seriously enough to root-cause it, rather than assuming a fix worked because it looked correct or because a similar-looking fix worked once before. Several fixes that looked obviously correct on first attempt — the dataset path fix, the worker-count increase — turned out to be wrong or actively harmful, and were only caught by verifying the actual result rather than trusting the reasoning that produced them.
